# Supabase 空库迁移与权限计划

## 现状与风险

本计划基于提交 `870c1f5` 的 37 个版本 SQL 及迁移目录外的 setup、upgrade、hotfix 和 dashboard 脚本。README 的安装方式依赖手工执行目录外脚本。当前自动迁移链的首个静态阻断是 `006_message_audio.sql` 对尚未创建的 `public.messages` 执行 ALTER。建表在 `setup_messages.sql`，而 `006` 检查的 `media_type` 还依赖 `upgrade_message_media.sql`。`007` 的情书基础表来自 `upgrade_couple_letters.sql`，封面、头像桶及成员资料／邀请重发／解绑函数也有目录外定义。历史版本号包含 `003` 和 `003001`，不要用文件名来推断云端已执行清单。原库与已部署版本未连接核实。

| 风险 | 证据与处理 |
| --- | --- |
| 邀请并发与第三成员 | `001` 锁单条邀请码后计数，无法独立保证不同邀请码对同一空间并发的成员上限。重发和离开在 `setup_account_management.sql`，离开只删成员行。新库加槽位硬约束，统一空间锁与邀请失效规则 |
| 隔离不完整 | `album_photos` 通过父相册推断租户。部分原策略按作者更新／删除。曾有权限的离开者仍可能触发仅按作者判断的 DML。所有业务行直接带空间键，写入同时检查实时成员关系和角色 |
| 混合迁移 | `011` 同时包含消息、清单、纪念日守卫、账号名与 AI。 `013` 同时配置来电与成员资料。抽取保留逻辑。 `030` 的注销函数直接操作 `music_room_messages/ai_saved_works/listening_sessions`；缺表时执行分支会报错 |
| 活动流泄露 | `036` 从源行提取 `content/note/answer_text`，将 INSERT、UPDATE、DELETE 都写进长期活动行。需要避免撤回消息、旧定位、隐藏正文及导出旁路，控制已读更新产生的噪音 |
| 保密时机 | `033` 的答案 SELECT 按情侣成员与题目归属校验，没有数据库级双方答完条件。UI 的延迟显示应同步到数据库读入口、活动流和导出。 `021` 未来邮箱以 RPC 隐藏未到期收件正文；`023` 声音胶囊按成员授权，本身没有定时解锁字段 |
| 账号删除 | `012/030` 和 `account-security` 跨业务表、Auth 管理 API 和存储；外键的 RESTRICT/CASCADE、历史空间及重试边界要逐个评估。现有改写历史作者给另一方的逻辑须明确处理展示和留存语义 |
| 额外 SQL 路径 | `dashboard_apply_pending.sql`、`setup*.sql`、`upgrade*.sql` 和 hotfix 作为考古依据。包含旧表清理或手工补丁的脚本不进入空库运行路径 |

## 新的版本化迁移链

在下一阶段提交新的唯一递增时间戳迁移，并把上游 SQL 保留在 Git 历史及只读归档路径。以下为依赖顺序，具体 SQL 由后续实施阶段提交。CLI 只维护一份活动迁移链，测试种子只含虚构账户和数据。

1. **身份和成员。** 建扩展、`profiles`、`couples`、`couple_members`、`invitations` 和注册授权。建立 `auth.users` 资料触发器、成员检查及创建、重发、接受、解绑 RPC。重用 `011/031/032` 的账号映射、限流、恢复码实现中的必要对象，密钥及哈希表放在服务端边界。
2. **核心业务。** 从 `setup_messages`、`upgrade_couple_letters`、封面 setup、`002/003001/004/005/006/007/011/014/019/020/022` 汇总最终结构与权限。创建相册、照片、消息、时光、手写情书、清单、纪念日、收藏、反应、评论。所有保留外键先于使用者建好，守卫触发器只装最终版本。
3. **拓展业务。** 合并 `021/023–026/033/034` 的未来邮箱、声音胶囊、彩蛋、故事分享、心情、问答、共享日历与事件任务。建立媒体对象元数据和业务关联，R2 使用独立私有桶，由 Worker 处理。对锁定内容通过受控读接口按服务器时间解封。
4. **独立打卡。** 按下节重写 `008/016–018` 的保留部分，保留双人语义、保护、历史和非宠物里程碑。
5. **活动、实时、注销。** 改写 `036`，挂接保留源表。只在明确的 publication 中发布必要的表，保留 `013` 的成员同步需求并改用最小资料接口。重写 `030` 注销，按每个 FK 决定删除、匿名化或留存，Auth 删除和 R2 对象回收使用持久任务与可重试状态。
6. **权限和契约验证。** 对每个 Data API 对象显式授权。以 pgTAP 或 SQL 加双会话 API 集成测试验收。从空实例连跑两次本地 reset 验证可重建，另对同实例执行 `migration up --local` 验证已应用版本跳过。破坏性重建仅用于本机的临时项目。

## 双人上限、邀请与数据隔离

- `couple_members` 增加 `slot smallint NOT NULL CHECK (slot IN (1,2))`、`UNIQUE (couple_id, slot)` 和 `UNIQUE (user_id)`。成员表禁止客户端直接增删改。创建、接受、重发、解绑统一锁 `couples` 行，再锁邀请码行。接受前可按 code 哈希定位空间，拿锁后重新检查当前成员、邀请方身份、有效期、撤销／使用状态和空槽位；插入成员和标记使用在同一事务。相同邀请最多成功一次；相同账号的跨空间并发靠唯一约束兜底。
- 生成高熵邀请码，只存哈希，对失败尝试限流，不进 URL、日志或导出。新发码撤销上一张未用邀请码，满员禁止发码。加入与退出同步更新授权；默认冻结曾经双人使用的空间，解绑后不让新成员读到前任共享历史。若同两人重绑或恢复有业务需求，用明确的授权及测试覆盖。
- 账户允许名单独立于情侣邀请码。使用两张单次注册许可，或让 Supabase 公开自助注册关闭、由现有受限服务端入口受控创建两名 Auth 用户。用户名、邮箱、OAuth、恢复流程若并存，均必须经过同一账户准入，客户端 UI 不承担准入职责。
- 所有共享行直接以不可任意修改的 `couple_id` 隔离。 `album_photos`、`daily_answers`、`shared_event_tasks`、媒体关联及互动数据使用 `(parent_id,couple_id)` 组合外键或等效的数据库强校验。多态评论目标需证明目标类型、ID 和空间同时匹配。全局题库、账号私有安全状态按角色或 `auth.uid()` 隔离，账号级字段不会因伴侣资料查询而公开。
- RLS 区分 SELECT、INSERT、UPDATE、DELETE。更新同时用 USING 和 WITH CHECK，写入派生作者与空间字段，禁止把行移到别的空间。消息发送者只能撤回自己的消息，另一成员只能对收到的消息标记已读。使用服务器时间和限定列／RPC。 `SECURITY DEFINER` 函数固定安全 `search_path` 并显式限定表名，取消 `PUBLIC` 执行权，只授必要角色。成员判断的对外签名不允许探测任意用户。
- 实时订阅仅在有效会话及绑定状态下启动，刷新 JWT、重连补拉并按 ID 去重。私有广播按有效成员授权。删除同步使用受控的事件／墓碑或重新拉取，不依赖 Postgres Changes 对 DELETE 进行行级过滤。解绑时清理频道、上传队列、签名 URL、对象 URL 和前端缓存。立即阻断新的查询及媒体授权，处理已连接频道和已签发短期 URL 的撤销窗口。[Supabase Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)

## 008 与 016–018 的拆分

| 版本 | 原职责与耦合 | 新库设计 |
| --- | --- | --- |
| `008_pet_streak` | 同建 `couple_pets`、`couple_streaks`、`streak_day_actions`。 `ensure_couple_pet()` 创建宠物及打卡状态。打卡、喂养 RPC 共享宠物 | `ensure_streak_state` 仅初始化 streak，打卡入口不触及宠物或其组合类型 |
| `016_streak_status` | 服务器以 `Asia/Shanghai` 计算业务日期，新增状态和写入 RPC，状态、连续数和保护逻辑仍带宠物 | 保留状态、当日两人的完成情况、当前／最长连续数、保护额度。服务端统一业务时区，初期沿用历史语义 |
| `017_streak_protection` | 新增 `record_couple_activity_core(date)` 并授 authenticated，外层再包装日期 RPC。后续 `018` 替换外层后，该 core 仍可存在 | 合并唯一公开写入口，废弃旧可调用 core。历史规则中漏一天且持有保护可消费一张，每累计到 7 的倍数获一张、上限 3，按用例核对边界 |
| `018_streak_history_rewards` | `record_couple_activity_context` 写明细和每日汇总后计数，随后锁 streak 行，调用依赖 `public.couple_pets` 参数的状态 helper，写宠物和奖励；历史 RPC 返回 rewards | 按空间在写入前串行化，确保双方并发最后一次不会都看到单人计数。区分每日动作、来源历史与里程碑。保留 3/7/14/30/100 天的纯里程碑，去掉宠物、家具、奖励键和等级映射 |

建议公共接口为 `get_couple_streak_status()`、`check_in_couple(p_request_id uuid, p_mood integer, p_note text)` 和 `get_couple_streak_history(p_month date)`。手动请求采用幂等 ID，同一用户每天只贡献一次，两名有效成员完成后同一天只结算一次。若恢复旧版消息、回忆、清单等可贡献签到的能力，以可信业务事件和源行去重触发。数据库拒绝客户端伪造来源、指定其他人或补签到。加入/解绑与结算共用空间锁，确定同日旧成员的历史保留和计数边界。历史按服务器日期归档，测试跨午夜、时区、两人并发、重试、漏一天消费、连漏复位、每 7 天补卡和上限。状态接口也需测试可保护的空档如何展示。

## 036 独立的通知与活动流

`public.record_couple_activity()` 是无参数触发函数，与旧 `record_couple_activity(date DEFAULT NULL)` 签到 RPC 同名但签名不同。重建为 `emit_couple_activity_event()`，删除 AI／音乐触发源和对应 kind/target，保留消息、回忆、相册、日历、清单、纪念日、手写情书、心情、问答和声音胶囊。去掉客户端 INSERT 策略，保留只读和必要的实时发布。活动只存最小类型、空间、主体 ID、时间和通用文案；受限正文由源表授权读取。只对业务相关变更发事件，删除或撤回后仍可显示通用状态，不留原文。测试所有保留触发器及 Realtime，对 SQL 吞异常造成的静默漏记安排日志和断言。

## 迁移验证与发布门槛

- 用本地 Supabase/Docker 或专用 CI PostgreSQL/Supabase 实例验证。匿名、情侣 A/B、第三账户 C 和另一测试空间 D 分别测试读、写、RPC、Realtime、媒体权限、导出、解绑后旧令牌。两连接同时接受同码和不同码，核对成员数和使用次数。直接用目录查询检查 FK、触发器、publication、ACL 与排除对象。
- 加载空库后跑真实 HTTP/Auth/RLS 用例，现有 SQL 文本正则测试继续用于结构回归。测试伪造父子空间、冒名创建活动、修改聊天正文、越权标记已读、提前读未来信件、越权读声音胶囊、篡改状态、跨租户媒体 ID 和账号注销失败重试。
- 若需要已有数据，独立做受控导出、只读盘点、脱敏演练、映射与校验。匹配 Auth 用户 ID、空间／内容、R2 对象和变体，逐项核对数量与哈希。先在新库演练，旧数据保留备份；旧坐标及排除模块不导入。远程备份、正式导入和切换另行安排，本阶段无远程 SQL 或生产数据操作。
